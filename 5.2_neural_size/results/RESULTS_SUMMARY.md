### Known data gap: `grey_fraction`
Every record in this results folder has `grey_fraction: null`. These runs predate the `grey_fraction` metric added to `parameter_sweep.py` (the density-greyness diagnostic). **Grey fraction is not available for any run currently on disk** — it will only populate for runs executed after that change. Re-running (even with `--resume`, since these parameter values are already marked "complete") will **not** backfill it; the affected configurations would need to be re-run from scratch (or `--no-resume`) to get grey fraction values.

### Folder structure note
Several subtrees under `results/` are doubly-nested (e.g. `.../cantilever_beam_two_point_256x192_0.15/grid/cantilever_beam_two_point_256x192_0.15/grid/...`), an artifact of an earlier `--out-dir` path bug. This report was built by scanning for all `runs/*.json` files regardless of nesting depth, so no data was missed, but the folder itself could use a manual cleanup pass. Going forward, new runs should land in `neural_size_results/` (the corrected default), not `results/`.

## 4. Findings

- **`mbb_beam_384x128_0.3` is essentially insensitive to model capacity.** Compliance barely moves across `hidden_layers` (301.83–302.24) or `grid` (301.83–301.88) — a spread of well under 0.2%. Bigger networks and finer grids just cost more compute time (up to 4× between the smallest and largest `hidden_layers` setting) for no meaningful quality gain on this problem.

- **`cantilever_beam_two_point_256x192_0.15` is clearly capacity- and resolution-sensitive.** Compliance improves monotonically as `hidden_layers` grows from (8,8)→(32,32) (231.4 → 206.0, a ~11% improvement) and plateaus after (32,32) — (64,64) does not improve further and costs 65% more time. `grid` shows the same pattern: coarsest grid (4) is 30% worse than finest (10), improving steadily and monotonically with grid size.

- **`roof_256x256_0.4` has very low, tightly-clustered compliance (~2.84–2.90) and is not sensitive to `hidden_layers` size** — differences across all four widths are within ~2%. Best result at (16,16), not the largest network. No `grid`/`k` data exists yet to know if resolution matters here.

- **`free_suspended_bridge_256x256_0.075` has an outlier at `grid=4`:** compliance jumps to 169.35, roughly 5× worse than every other grid setting (all ~31–33) despite hitting the volume target almost exactly (violation ≈ −5×10⁻¹²). This looks like the optimizer converging to a degenerate/poor local optimum at very coarse grid resolution rather than a real trend — worth opening `free_suspended_bridge_256x256_0.075_grid_4_topology.png` to visually confirm before treating grid=4 as a valid data point. `k=1` also underperforms `k=2`/`k=3` (35.6 vs ~31–33), consistent with too-low spline order limiting expressiveness. Note `hidden_layers=(64,64)` and `grid=10`/`k=3` all report the same compliance (32.8396) — expected, since `(64,64), grid=10, k=3` is the shared baseline configuration reused across sweeps for this problem.

- **Runtime scales with capacity as expected**, roughly linearly with `hidden_layers` width and with `grid` size, on this single-worker (no-multiprocessing) HPC configuration. The largest single run (`roof`, `hidden_layers=(64,64)`) took ~2.8 hours; most runs fall in the 30 min–2.5 hr range at 400 steps.

- **Volume constraint is reliably satisfied everywhere** — violations are all ≲2×10⁻⁵ in magnitude, so none of the compliance differences above are confounded by volume-fraction drift.
